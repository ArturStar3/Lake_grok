1. Архитектура

Production-контур — три контейнера Docker и PostgreSQL на хосте Windows:

СервисПортРоль
frontend5173Веб-интерфейс (собранная статика, vite preview)
backend8000API и Django Admin (Gunicorn)
tileserver8080Векторная карта из map.mbtiles
PostgreSQL5432БД на хосте (DB_HOST=host.docker.internal)

Запуск всегда через два файла compose: docker-compose.yml + docker-compose.server.yml. Второй отключает bind-mount исходников frontend и поднимает production-образ.

Ветка git на сервере — только production. Разработка ведётся на develop_report (и других ветках) на машине разработчика.

2. Первый запуск

Пошаговая инструкция вынесена в файл PRODUCTION_LAUNCH.md в корне проекта. Краткий чек-лист:

  1. Docker Desktop + PostgreSQL + Git установлены.
  2. Проект на диске, ветка production.
  3. tileserver/data/map.mbtiles на месте.
  4. backend/.env из .env.example, DEBUG=False.
  5. docker load образов → import-and-start.ps1 или compose up с server-override.
  6. createsuperuser, проверка URL :5173 / :8000 / :8080.

3. Повседневные операции

3.1. Старт / останов

cd D:\InfoLake\Lake_grok
docker compose -f docker-compose.yml -f docker-compose.server.yml up -d --no-build --pull never
docker compose -f docker-compose.yml -f docker-compose.server.yml down

3.2. Статус и логи

docker compose -f docker-compose.yml -f docker-compose.server.yml ps
docker compose -f docker-compose.yml -f docker-compose.server.yml logs --tail 100
docker compose -f docker-compose.yml -f docker-compose.server.yml logs -f frontend

3.3. Проверка доступности

  • http://localhost:5173 — интерфейс
  • http://localhost:8000/admin/ — админка
  • http://localhost:8000/api/v1/ — API
  • http://localhost:8080/ — TileServer

На офлайн-сервере запрещено: docker compose build, docker compose pull, docker pull. Образы приходят только через docker load / пакет обновления.

4. Обновления

4.1. Для оператора

  1. Получить от разработчика infolake_update_vX.Y.Z.tar (или папку пакета).
  2. Распаковать в любую папку (например D:\InfoLake\updates\v1.0.1).
  3. Дважды щёлкнуть apply-update.bat.
  4. Дождаться зелёного баннера «ОБНОВЛЕНИЕ ЗАВЕРШЕНО».

Скрипт автоматически:

  • создаёт резервную копию PostgreSQL в backups\;
  • применяет код из update.bundle (fast-forward ветки production);
  • загружает Docker-образы из images.tar;
  • перезапускает контейнеры, выполняет migrate и seed шаблонов отчётов;
  • проверяет HTTP-доступность frontend / backend / tileserver.

4.2. При ошибке

Красный баннер «ОШИБКА — ВЫПОЛНЕН ОТКАТ» означает: скрипт вернул код и образы к состоянию до обновления. Не пытайтесь чинить вручную. Отправьте разработчику файл logs\update-YYYYMMDD_HHMMSS.log.

4.3. Для разработчика (сборка пакета)

git checkout production
# после merge из develop_report и bump VERSION / CHANGELOG
.\scripts\production\prepare-update-package.ps1

Результат: dist\updates\infolake_update_vX.Y.Z\ и .tar.

5. Резервные копии и восстановление

5.1. Автобэкап перед обновлением

apply-update.ps1 вызывает scripts\offline\backup-postgres-before-migrate.ps1 → файл backups\infolake_pre_migrate_*.dump (формат custom, pg_dump -Fc).

5.2. Ручной бэкап

.\scripts\offline\backup-postgres-before-migrate.ps1

5.3. Восстановление (только с участием разработчика / опытного админа)

docker compose -f docker-compose.yml -f docker-compose.server.yml down
pg_restore -h localhost -U infolake -d infolake_db --clean --if-exists backups\infolake_pre_migrate_XXXX.dump
docker compose -f docker-compose.yml -f docker-compose.server.yml up -d --no-build --pull never

Автоматический откат БД скриптом обновления не выполняется. Откатываются код и Docker-образы; БД откатывают вручную из dump при необходимости.

Также сохраняйте копии backend\media и tileserver\data\map.mbtiles.

6. Пользователи и права

  • Суперпользователь: createsuperuser (см. PRODUCTION_LAUNCH.md).
  • Группы безопасности: Django Admin → группы; страны + уровни модулей (none / read / write / write_delete).
  • Регистрация: статус pending → одобрение в «Управление пользователями».
  • Сброс пароля: админ выдаёт временный пароль; пользователь обязан сменить его.
  • Примеры групп: seed_security_groups.

Подробности API и JWT: backend/docs/OFFLINE_AUTH.md.

8. Страницы ошибок

  • Frontend 404 — неизвестный URL в браузере (не карта/логин).
  • Frontend ErrorBoundary — сбой отрисовки React; кнопка «Обновить страницу».
  • Backend 404/500 — HTML-шаблоны при DEBUG=False (админка, редкие HTML-запросы к Django).

API по-прежнему отвечает JSON-ошибками (стандарт DRF).

9. Диагностика

СимптомДействие
Карта пустая Проверить наличие tileserver/data/map.mbtiles, логи tileserver
Backend не стартует / ошибка БД DB_HOST, пароль, PostgreSQL запущен, firewall
Frontend «завис», docker kill не помогает См. OFFLINE_MIGRATION.md §8.1: wsl --shutdown, лимиты памяти, production compose
apply-update: «не fast-forward» Локальная история расходится — эскалация разработчику, не править git вручную
Медиа/фото 404 при DEBUG=False Убедиться, что том backend/media на месте; код отдаёт media через Django

10. Эскалация разработчику

Перед обращением соберите:

  1. Файл logs\update-*.log (если сбой обновления).
  2. Вывод docker compose … ps и logs --tail 200.
  3. Содержимое VERSION и результат git log -1 --oneline.
  4. Краткое описание: что делали, время, воспроизводится ли после reboot.
