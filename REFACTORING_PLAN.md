# InfoLake: анализ кода и план рефакторинга

Дата: 01.10.2026. Основа анализа — текущая рабочая копия, включая существующие незакоммиченные изменения и новые модули.

Статус исполнения: реализована кодовая часть первой волны (этапы 0–3) и отдельные ранние исправления; проверки, ограничения и оставшиеся задачи описаны в [REFACTORING_PROGRESS.md](REFACTORING_PROGRESS.md). Исходный анализ ниже сохранён как baseline. Production-приёмка и этапы 4–9 не объявляются завершёнными.

## 1. Основной вывод

Проект уже имеет полезное разделение на Django-приложения, сервисы и React-хуки. Главная проблема — неодинаковая глубина этого разделения: часть модулей стала фасадами, но крупные координаторы интерфейса и импорта продолжают совмещать несколько самостоятельных процессов. Первоочередная работа — исправить конкретные риски импорта и обновления, закрепить контракты проверками, затем продолжить декомпозицию.

Полная перепись приложения не требуется. Работы следует выполнять небольшими изменениями с сохранением API, структуры импортируемых архивов, идентификаторов карты и офлайн-запуска.

## 4. Реестр проблем

Приоритеты: **P0** — доступ к данным, файловые границы или целостность обновления; **P1** — корректность, конкурентность и значимая производительность; **P2** — поддерживаемость и последующая оптимизация.

«Подтверждено кодом» означает наличие конструкции в текущей реализации. Это не означает, что выполнялся эксплуатационный сценарий. Для рисков конкуренции, XSS/загрузки ресурсов и производительности воспроизведение должно входить в будущую работу.

### R01. Границы чтения media и лимиты ZIP — P0

Основание: [bundle_import.py](backend/data_exchange/services/bundle_import.py), `_extract_zip` (строка 59), `_attach_media` (365).

`rel_path` из импортируемых данных соединяется с staging-каталогом без проверки итогового пути. Абсолютный путь или `..` могут направить чтение вне каталога конкретной сессии. Для ZIP используется `extractall` без прикладных лимитов количества элементов, распакованного объёма и размеров JSON. Нельзя выводить наличие Zip Slip только из `extractall`: стандартная библиотека обрабатывает часть опасных имён; независимый риск находится в последующем чтении `rel_path`.

Изменение: единый resolver путей с проверкой `resolve()` и принадлежности разрешённому корню; запрет абсолютных путей и выхода через ссылки. Проверка списка ZIP-элементов до распаковки, лимиты объёма/количества/степени сжатия и потоковый контроль фактически прочитанных байтов. Проверка типов и структуры manifest/data до анализа сущностей.

Приёмка: некорректный архив отклоняется предсказуемой ошибкой; чтение вне staging невозможно; ошибка анализа не оставляет бесконтрольные временные файлы. Проверки используют искусственные архивы и временные каталоги.

### R02. Доступ к сессиям и странам при импорте — P0

Основание: [data_exchange/views.py](backend/data_exchange/views.py), строки 48, 67, 74, 83; [bundle_import.py](backend/data_exchange/services/bundle_import.py), `analyze_bundle` и `apply_import_session`.

Сессии получаются через `ImportSession.objects.get(pk=pk)` без ограничения по `created_by`. Модульные права проверяются, но объектная политика владельца не применяется. Пользователь передаётся в анализ для записи автора; применение не получает пользователя и не проверяет разрешённые ему страны. Экспорт, напротив, фильтрует страны.

Изменение: определить и реализовать общую политику доступа к сессии: владелец и явно разрешённый административный доступ либо документированная общая работа. Передавать инициатора в применение и проверять все затрагиваемые страны и глобальные справочники. Отделить право импортировать данные от возможности менять общие справочники, если это требуется принятой моделью прав.

Приёмка: два пользователя с разными странами не получают и не изменяют чужие данные через UUID сессии/сущности; отказ происходит до применения. Результат 403/404 соответствует существующим соглашениям. Если совместные сессии нужны продукту, они получают явную политику вместо неограниченного доступа.

### R03. Несоответствие production-образов в обновлении — P0

Основание: [prepare-update-package.ps1](scripts/production/prepare-update-package.ps1), строки 60, 87–100; [apply-update.ps1](scripts/production/apply-update.ps1), строки 112–113, 218–221; [docker-compose.server.yml](docker-compose.server.yml).

Подготовка собирает production-режим с `infolake-nginx`, но сохраняет и версионирует `infolake-frontend`. Откат также возвращает frontend-образ, а не production-nginx. Возможны отсутствие нужного образа на целевой машине или запуск прежней SPA. Это подтверждённое расхождение конфигураций, а не предположение о нагрузке.

Изменение: получать полный набор образов из конкретного Compose-режима, как уже делает основной экспорт; version/rollback-tags назначать всем обновляемым прикладным образам. В манифесте фиксировать режим, Git SHA и image IDs/digests. Для Postgres/direct предусмотреть соответствующие overlays.

Приёмка: состав пакета совпадает с `config --images` выбранного режима; запуск и откат возвращают согласованные backend и SPA. Испытать на отдельной установке без Интернета.

### R04. Backup, происхождение сборки и откат схемы — P0

Основание: [prepare-update-package.ps1](scripts/production/prepare-update-package.ps1), `Assert-OnProductionBranch` и `git bundle create`; [apply-update.ps1](scripts/production/apply-update.ps1), блок backup (201), `Invoke-Rollback`; [docker-entrypoint.sh](backend/docker-entrypoint.sh).

Подготовка допускает сборку текущей ветки, тогда как bundle создаётся из `production`: код в образе и поставляемый Git-коммит могут различаться. Обновление продолжает работу после неудачного или отсутствующего backup. Откат кода/образов не восстанавливает схему БД, а entrypoint автоматически применяет миграции. Сообщение «выполнен откат» поэтому не доказывает восстановление системы.

Изменение: сборка из одного зафиксированного чистого коммита в отдельном checkout; проверка SHA всех артефактов. Перед изменением схемы успешный и проверенный backup обязателен. Разделить восстановление образов, кода, схемы и данных; использовать совместимые поэтапные миграции. Определить один управляемый шаг миграции и исключить одновременные повторные вызовы при обновлении.

Приёмка: ошибка backup останавливает обновление до изменений; несовпадение SHA отклоняется; rollback-процедура отработана на копии БД. Сначала проверяется совместимость прежнего приложения с новой схемой, а при её отсутствии применяется документированное восстановление. Данные рабочей системы не используются для испытаний без резервной копии.

### R05. Файлы и повторное применение импорта — P1

Основание: [bundle_import.py](backend/data_exchange/services/bundle_import.py), строки 376, 437–495.

Применение атомарно для БД, но `field.save` записывает файлы до коммита, а staging удаляется внутри транзакции. Откат БД не отменяет файловую запись. Сессия не блокируется через `select_for_update`, причём статус APPLYING допускает вход в применение. Одновременные resolve могут повторно применить данные.

Изменение: блокировка и повторное чтение сессии внутри транзакции; определённые переходы состояний и идемпотентность. Удаление staging — после успешного коммита. Для новых файлов — учёт операций и компенсационная очистка при неуспехе либо подготовка файлов с управляемым завершением. Один `on_commit` сам по себе не решает все случаи согласованности файлов и БД.

Приёмка: повторный запрос не создаёт дубликаты; два параллельных запроса не применяют одну сессию одновременно; искусственная ошибка после записи файла не оставляет потерянный staging или неучтённые media. Конкурентность проверяется на PostgreSQL.

### R06. HTML/SVG и загрузка ресурсов PDF — P0/P1

Основание: [markdown_render.py](backend/infolake/markdown_render.py), строка 9; [validators.py](backend/formular/validators.py), строка 16; [pdf_builder.py](backend/reports/services/pdf_builder.py), строка 77; [collectors.py](backend/reports/services/collectors.py), строка 325; [svgUtils.js](frontend/src/utils/svgUtils.js); [formular/admin.py](backend/formular/admin.py), SVG preview.

Серверный Markdown допускает HTML и помечает результат безопасным без очистки. SVG проверяется по расширению и MIME, вычисленному из имени, а затем встраивается в HTML. PDF получает HTML из Markdown и не задаёт ограниченный загрузчик ресурсов. Это создаёт поверхность для активного содержимого и внешних/локальных URL; фактическое воздействие зависит от контекста, CSP, авторства данных и renderer и требует отдельных тестов.

Изменение: единая политика допустимого содержимого Markdown/SVG, очистка на доверенной серверной границе и безопасный preview. Для PDF — resolver, разрешающий только необходимые локальные assets/media, с ограничением пути и размера; запрет внешней сети и произвольного `file:`. Сохранить допустимые классы палитр, gradients и ссылки внутри SVG.

Приёмка: пользовательский контент не выполняет код, не загружает внешние ресурсы и не читает произвольные файлы при экспорте. Русский текст, таблицы, палитры и существующие корректные маркеры отображаются. Выбор дополнительного sanitizer — отдельное обоснование зависимости; не использовать регулярные выражения как универсальный HTML-sanitizer.

### R07. Кэш справочников не привязан к авторизации — P1

Основание: [useReferenceData.js](frontend/src/hooks/useReferenceData.js), строки 9–11, 55–102; [AuthContext.jsx](frontend/src/context/AuthContext.jsx), login/logout.

Общий кэш сохраняется в памяти модуля до пяти минут и не сбрасывается на login/logout. В одной вкладке следующий пользователь может увидеть справочники из предыдущего контекста доступа. Общий запрос принадлежит сигналу первого потребителя: закрытие одной формы отменяет загрузку для остальных. Инвалидация обнуляет promise, но старый запрос может позже восстановить устаревший кэш; режим `includeMarkerSvgs` также не входит в ключ.

Изменение: ключ по сессии/контексту прав и режиму данных; сброс при смене пользователя; поколение кэша для запрета устаревших результатов. Разделить общий запрос и отмену подписки потребителя. Выделить SVG-каталог в отдельный ресурс.

Приёмка: смена пользователя, две одновременно открытые формы, закрытие одной формы и обновление справочника во время загрузки дают актуальные данные без взаимного прерывания. Backend-права остаются обязательными независимо от кэша UI.

### R08. Несколько входов в refresh и глобальные Axios interceptors — P1

Основание: [axios.js](frontend/src/config/axios.js), строки 76, 106, 139; [AuthContext.jsx](frontend/src/context/AuthContext.jsx), refreshMe и периодическое обновление.

Объединение refresh-запросов действует в обработчике 401, но прямые вызовы `refreshAccessToken` из контекста обходят этот механизм. Возможны параллельные обновления и запись результата после logout/нового login. Bearer подключён также к глобальному Axios, что затрудняет контроль адресатов; `apiClient` используется и для абсолютных media URL.

Изменение: единственная функция refresh с общим promise и поколением авторизации; старый результат не записывается после смены сессии. Все API-запросы постепенно перевести на явный клиент, выдачу токена ограничить проверенным API-origin. Публичные auth-исключения и сетевые ошибки сохранить. Отдельно определить требуемую серверную семантику logout: сейчас он только пишет аудит, без отзыва refresh-токена.

Приёмка: серия 401, одновременный таймер и запрос, ошибка сети, logout во время refresh и новый login проходят без восстановления старой сессии. Изменение серверного logout требует отдельной спецификации и миграций, если вводится хранение отзыва.

### R09. Ограничение входа зависит от процесса и доверия к IP — P1

Основание: [rate_limit.py](backend/accounts/services/rate_limit.py); [permissions.py](backend/accounts/permissions.py), `get_client_ip` (112); [settings.py](backend/infolake/settings.py), `CACHES`; [docker-compose.yml](docker-compose.yml), два Gunicorn workers.

Для UI-автоматизации отдельно согласовать расширение тестового инструментария и его offline-подготовку. Добавить отдельные test-settings для PostgreSQL и миграций, не подключая рабочую БД.

Приёмка: команды воспроизводимы локально и в контейнере; проверки выполняются до сборки релизного пакета; результаты записываются в release manifest. Проверять нужные сценарии, а не процент покрытия ради процента.

### R25. Конвертер и документация — P2

Основание: [coords.py](converter/coords.py), `_DMS_BODY_RE.search`; [xlsx_io.py](converter/xlsx_io.py), convert_sheet; [app.py](converter/app.py), `_convert_batch`; прежние документы анализа.

Конвертация запускается синхронно из Tkinter handler, поэтому крупный набор файлов может блокировать окно. Лист читается в память и переписывается; сохранение формул, оформления и неподдерживаемого содержимого требует явной спецификации. DMS-parser использует поиск фрагмента вместо полного совпадения, что допускает принятие части некорректной строки.

Изменение: строгие unit-тесты парсинга и round-trip, явная политика сохранения Excel, безопасная запись результата и прогресс пакетной обработки. Фоновая обработка не обращается напрямую к Tkinter widgets. Актуализировать старые планы и дать им ссылку на этот документ; эксплуатационные инструкции оставить в существующих OFFLINE/PRODUCTION документах.

Приёмка: неверная строка не принимается частично, точность соответствует шести знакам DD, исходный файл сохраняется; на больших файлах окно отвечает. Converter остаётся самостоятельной утилитой.

## 6. Контракты, которые нельзя сломать

| Контракт | Требование к изменениям |
| --- | --- |
| `/api/v1/`, endpoint paths, UUID, сериализованные поля | Сохранить текущие имена и типы; новые aggregate/map/pageable endpoints вводить дополнительно |
| Module permissions, страны, 403/404 | Авторизация на сервере; тестировать чтение, запись, удаление и связанных сущностей |
| `Target.actions`, deployed_equipment, geometry/metadata | Согласованные read/write представления и сохранение поддерживаемых modes |
| Bundle manifest/data, natural keys, ENTITY_ORDER | Совместимые корректные архивы продолжают импортироваться; смена формата — с версией и migration-path |
| Demo stages, sequence, mosaic/tableau, media | Сохранить поля, defaults и старые сценарии; общие контрактные примеры Python/JS |
| MapLibre IDs и unifiedLayerMapping | Изменение источника и mapping проверяется вместе; glyphs/sprites/tiles остаются локальными |
| `media` и `static` | Сохранить доступные пути; не включать рабочие файлы в образ и не удалять существующие загрузки |
| Proxied/direct URL | Браузер использует current hostname/same-origin; Docker DNS остаётся только внутри сети |
| Offline production | `--no-build --pull never`; подготовка зависимостей и сборка только до переноса |
| Модели и миграции | Сохранить app labels/table names при переносе; схему менять отдельными reviewed migrations |
| Исторические Python imports | Фасады сохраняют имена для сидов, management-команд и старых миграций |

Для маршрутов media отдельно определить требование конфиденциальности. Сейчас Nginx `/media/` и Django serve не используют модульные/страновые permissions. Перевод на защищённую выдачу меняет контракт загрузки `<img>/<video>` и может потребовать отдельного продуктового решения; UUID/непредсказуемое имя не заменяют проверку доступа.

## 7. Проверки на каждом этапе

### Backend

Из `backend/` в рабочем Python-окружении либо через уже запущенный backend-контейнер:

```text
python manage.py check
python manage.py test <затронутый app или test-label>
python manage.py test --verbosity=1
```

Для изменений моделей дополнительно `python manage.py makemigrations --check --dry-run` и review новых миграций. SQLite runner не проверяет существующие миграции; миграционный граф и применение проверять отдельно на временной PostgreSQL-БД с копией/фикстурами. До этой проверки не считать этап со schema changes завершённым.

### Frontend

Из `frontend/`:

```text
npm.cmd run lint
npm.cmd run build
```

В shell без PowerShell policy-ограничения эквивалентны `npm run lint` и `npm run build`. При аудите сборка должна идти в отдельную новую временную папку, если `dist` содержит пользовательские артефакты. Проверки JS/UI добавляются по R24; не ссылаться на несуществующий `npm test`.

После изменений карты вручную проверить vector и raster fallback, toggles, selection/clustering, fullscreen, измерения, рисование и режим embed. Для demo — pause/resume/seek/stop, hidden tab, slow media, повторный запуск и cleanup таймеров. Число предупреждений фиксировать по затронутым файлам; baseline 85 не превращать в разрешение добавлять новые.

### Конфигурации и выпуск

Из корня проекта, без запуска сервисов:

```text
docker compose -f docker-compose.yml -f docker-compose.server.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.server.yml -f docker-compose.postgres.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.direct.yml --profile direct-prod config --quiet
docker compose -f docker-compose.yml -f docker-compose.direct.yml --profile dev config --quiet
```

Postgres overlay требует корректный root `.env` с `POSTGRES_PASSWORD`; значения не выводить. Если меняется источник стилей, выполнить `npm run build:map-style` из frontend и проверить оба outputs; для прочих работ генератор не запускать.

На тестовой установке выполнить `nginx -t`, проверку `/`, `/api/v1/`, `/admin/`, `/tiles/styles/infolake-unified/style.json`, media/static, restart upstream и offline-запуск. Для релиза проверить соответствие манифестов prod/prod_postgres и точных образов; большие `.tar` не коммитить. Детали запусков и backup брать из [PRODUCTION_LAUNCH.md](PRODUCTION_LAUNCH.md), [OFFLINE_MIGRATION.md](OFFLINE_MIGRATION.md), [OFFLINE_DIAGNOSTICS.md](OFFLINE_DIAGNOSTICS.md) и mode-specific документов.

## 8. Критерии завершения программы

- Закрыты P0 по импорту и обновлению; принята и проверена политика HTML/SVG/PDF.
- Backend-тесты, frontend lint/build и конфигурации поддерживаемых режимов проходят; PostgreSQL/migrations проверены отдельно.
- Основные workflows имеют понятного владельца состояния, а перемещение между формой и картой не теряет черновик.
- Контрактные fixtures сохраняют совместимость старых API, demo-сценариев и корректных bundles.
- Обновление и откат воспроизводимо возвращают согласованные код, SPA, образы и данные.
- Измерены и сравнены начальная загрузка, карта, отчёты, архивы и LOS; оптимизации подтверждены измерениями.
- Нет новых внешних зависимостей офлайн-runtime, незапланированных изменений schema или удаления пользовательских ресурсов.
- Документация и манифесты отражают итоговое поведение, а каждый выполненный пункт имеет ссылку на изменение и его проверку.
